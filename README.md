## Alma ↔ Bitrix24 Bridge

Интеграционный PHP‑проект для синхронизации объектов недвижимости между Bitrix24 и внешним сервисом Alma (апартаменты, юниты/комнаты, контракты и т.п.). Скрипты вызываются из Bitrix24 (веб‑хуки, роботы, бизнес‑процессы) и по REST API общаются с Alma.

---

## 1. Обзор

- **Назначение**: связать CRM Bitrix24 и систему недвижимости Alma, чтобы:
  - создавать и обновлять апартаменты и юниты/комнаты в Alma по данным из Bitrix24;
  - синхронизировать статусы, типы контрактов, аренды и др. справочники;
  - вести детализированное логирование операций по объектам.
- **Города/проекты**: поддержка нескольких проектов (например, `Dubai`, `HongKong`) с разными маппингами полей.


## 2. Технологический стек и требования

- **Язык**: PHP **8.0+**
- **Веб‑сервер**: Nginx или Apache
- **PHP‑расширения**:
  - `curl`
  - `json`
  - `mbstring` (рекомендуется)
  - `openssl` (для HTTPS‑запросов к Alma и Bitrix24)
- **Внешние системы**:
  - Доступ к **Bitrix24** c настроенным входящим веб‑хуком.
  - Доступ к **Alma API** (ключ `ALMA_API_KEY` и базовый URL `ALMA_API_URL`).

Проект не использует Composer: это набор PHP‑скриптов, подключаемых напрямую веб‑сервером.

---

## 3. Структура проекта

Проект разделён на несколько логических частей:

- **`Api/` — сценарии синхронизации и клиенты Alma**  
  Здесь находятся все PHP‑скрипты, которые вызываются из Bitrix24 и/или ходят в Alma:
  - общие клиенты Alma:
    - `BaseApi.php` — базовый клиент Alma (запросы, ошибки, формат ответов);
    - `UnitApi.php` — работа с юнитами/комнатами;
    - `ClientApi.php` — создание, поиск и обновление клиентов Alma;
  - синхронизация объектов недвижимости:
    - `AppartApi.php` — синхронизация апартаментов между Bitrix24 и Alma;
    - `RoomApi.php` — синхронизация комнат/юнитов, связанных с апартаментами;
  - синхронизация договоров:
    - `TenantContractApi.php` — договоры арендаторов;
    - `LandlordContractApi.php` — договоры с собственниками;
  - служебные сценарии:
    - `BlockingAppartApi.php` — создание и обновление блокирующих контрактов по данным списков Bitrix24;
    - `TerminationAppartApi.php` — создание и архивирование расторгающих контрактов по датам отказа;
    - `ContactSync.php` — синхронизация контактных данных между Bitrix24 и Alma.

- **`Core/Config/` — конфигурация проектов**  
  - `Config.php` — чтение настроек окружения из `config.env`;
  - `ProjectMapping.php` — описание всех маппингов полей и справочников для разных проектов/городов (Dubai, HongKong и т.п.).

- **`Core/` — общая инфраструктура**  
  - `Bitrix24Rest.php` — клиент для REST Bitrix24 (обращения к вебхуку);
  - `Logger.php` и `*ActionLogger` — логирование операций интеграции и действий с сущностями.

- **`logs/` — журналы работы**  
  Логи по проектам и датам, основное место для анализа того, какие синхронизации выполнялись и с каким результатом.

## 4. Конфигурация

### 4.1. Файл окружения `config.env`

Все основные настройки проекта хранятся в файле `config.env` рядом с кодом. В нём вы заполняете:

- ключ и адрес API Alma (`ALMA_API_KEY`, `ALMA_API_URL`);
- идентификаторы и веб‑хуки проектов Bitrix24 (`PROJECT_DUBAI_*`, `PROJECT_HONGKONG_*` и т.п.);
- при необходимости — другие параметры окружения.


### 4.2. Маппинги проектов (`ProjectMapping`)

Класс `ProjectMapping` задаёт:

- связи между проектами (`Dubai`, `HongKong`, …) и:
  - ID смарт‑процессов/сущностей Bitrix24;
  - кодами пользовательских полей (апартаменты, юниты, контракты, арендаторы, лендлорды);
  - перечислениями типов аренды, типов контрактов, стадий сделок и т.д.

Скрипты используют эти маппинги, чтобы правильно читать поля Bitrix24 и собирать данные для Alma под каждый проект.

Выбор проекта осуществляется параметром `project` в HTTP‑запросе (по умолчанию `Dubai`).

## 5. Развёртывание

1. **Клонируйте репозиторий** в директорию, из которой веб‑сервер обслуживает PHP‑файлы:
   ```bash
   git clone <repo-url> /path/to/project
   ```
2. **Создайте файл `config.env`** в корне проекта по примеру выше и заполните:
   - ключи Alma (`ALMA_API_KEY`, `ALMA_API_URL`);
   - ID и веб‑хуки проектов Bitrix24 (`PROJECT_*_WEBHOOK_URL` и т.п.).
3. **Проверьте права доступа**:
   - PHP‑процесс должен иметь права на чтение `config.env`;
   - директория `logs/` (создаётся автоматически) должна быть доступна на запись.
4. **Настройте виртуальный хост** (Nginx/Apache), чтобы URL вида:
   - `https://your-domain.com/Api/RoomApi.php`
   обрабатывался этим проектом.

Composer‑зависимостей нет, установка через `composer install` не требуется.

## 6. Интеграция с Bitrix24

### 6.1. Получение веб‑хука

1. В Bitrix24 откройте **Разработчикам → Вебхуки**.
2. Создайте входящий веб‑хук с правами на работу с CRM (смарт‑процессы/лиды/сделки в зависимости от вашей схемы).
3. Скопируйте URL и пропишите его в `config.env` как `PROJECT_<NAME>_WEBHOOK_URL`.

### 6.2. Вызов скриптов из роботов/бизнес‑процессов

Для синхронизации комнаты/юнита:

- создайте робота/действие бизнес‑процесса в смарт‑процессе комнаты;
- настройте HTTP‑запрос **GET** на URL:

```text
https://your-domain.com/Api/RoomApi.php?id={=Document:ID}&project=Dubai
```

- `id` — идентификатор комнаты (юнита) в Bitrix24;
- `project` — имя проекта, совпадающее с ключами в `ProjectMapping` (`Dubai`, `HongKong`, …).

При срабатывании робота скрипт:

1. Получит данные комнаты через `crm.item.get` по `entityTypeId` для юнита.
2. Считает ID апартамента, тип аренды и другие поля согласно маппингу.
3. Создаст или обновит соответствующую комнату в Alma.

## 7. Работа с Alma API

Скрипты обращаются к Alma по HTTP с заголовками:
  - `Api-Key: <ALMA_API_KEY>`
  - `Content-Type: application/json`
  - `Accept: application/json`
- формат тела: JSON.

Пример данных, отправляемых при синхронизации комнаты (`RoomApi.php` → `UnitApi::upsertRoom`):

```json
{
  "external_id": "123",
  "name": "Room 123",
  "header": "Room 123",
  "goal_rent_cost": 4500,
  "internal_area": 15.5,
  "photos": [],
  "property_type": "room",
  "number": "1",
  "parent_unit": 987
}
```

- `external_id` — ID комнаты в Bitrix24;
- `parent_unit` — ID апартамента в Alma, найденный по `external_id` апартамента;
- `goal_rent_cost` и `internal_area` берутся из полей комнаты по маппингам проекта;
- `number` маппится из справочника (например, `SP1-1`, `SP2-1` и т.п.).

Даты передаются в формате Alma `YYYY-MM-DDT00:00:00Z`; при некорректных датах запрос считается невалидным.

## 8. Примеры запросов и ответов

### 8.1. Запрос на синхронизацию комнаты

```http
GET /Api/RoomApi.php?id=123&project=Dubai HTTP/1.1
Host: your-domain.com
```

### 8.2. Успешный ответ

Типичный успешный ответ выглядит так:

```json
{
  "success": true,
  "code": 200,
  "response": {
    "id": 456,
    "external_id": "123",
    "name": "Room 123"
  },
  "method": "POST"
}
```

- `code` — HTTP‑код, полученный от Alma;
- `response` — тело ответа Alma;
- `method` — фактический метод, использованный при обращении к Alma (`POST` или `PATCH`).

### 8.3. Ошибочный ответ

При ошибках API возвращает JSON в схожем формате:

```json
{
  "success": false,
  "code": 400,
  "response": {
    "message": "Validation error: Apartment ID not found in room"
  },
  "method": "ERROR"
}
```

Типичные случаи:

- `400` — ошибка валидации входных параметров (например, не передан `id`, не найден `apartmentId` в данных комнаты);
- `404` — объект не найден в Alma (например, апартамент ещё не синхронизирован);
- `500` — внутренняя ошибка запроса к Alma или Bitrix24.

### 8.4. Типичные специфические ошибки Alma API

- **Пересечение периодов использования юнита (конфликт дат)**  
  Пример ответа:

  ```json
  {
    "message": "API error: API request failed (400): {\"non_field_errors\":[\"There are intersections in the use of the unit. Nearest intersection usage id:21418 usage type=tenant.\"]}"
  }
  ```

  Означает неуспешную попытку создать или обновить контракт, даты которого пересекаются с уже существующим использованием этого юнита. Нужно проверить сначала юнит и затем контракты по нему на пересечения.

- **Клиент с таким email уже существует (при создании лендлорда или другого контакта)**  
  Пример ответа:

  ```json
  {"email": "Client with received email already exists"}
  ```

  Означает, что в Alma уже зарегистрирован клиент (лендлорд, арендатор и т.п.) с точно таким же email — повторное создание запрещено.  
  Также в Alma есть особенность: если пользователь с таким email уже приглашён как сотрудник, то его нельзя пригласить как жильца/собственника.  
  Кроме того, если клиент был создан вручную в Alma, то поле `external_id` (по сути ID контакта в Битрикс24) не заполнено и синхронизация не произойдёт.

- **Обязательное поле `last_name` не заполнено (при синхронизации контакта)**  
  Пример ответа:

  ```json
  {"last_name": ["This field may not be null."]}
  ```

  Означает, что в данных контакта отсутствует обязательное поле «фамилия» (`last_name`), из-за чего Alma отклоняет запрос на создание/обновление.

## 9. Логирование и отладка

- Все логи пишутся в директорию `logs/`, разложены по проектам и датам.
- Лог‑записи содержат:
  - время (`timestamp`);
  - уровень (`DEBUG`, `INFO`, `WARNING`, `ERROR`);
  - текст сообщения и контекст (ID сущностей, детали запроса/ответа и т.д.).
- Для ошибок Alma и Bitrix24 в лог попадает:
  - HTTP‑код;
  - укороченное тело ответа;
  - тип исключения, стек вызовов (для неожиданных ошибок).

При отладке:

- проверьте логи по нужному проекту и дате;
- убедитесь, что поля и ID в `ProjectMapping` соответствуют фактическим кодам в Bitrix24;
- проверьте, что URL веб‑хука Bitrix24 и `ALMA_API_URL` корректны и доступны с сервера.

## 10. Соглашение по неймингу

Чтобы код оставался единообразным и коротким, используем следующие правила:

- Для методов создания/обновления используем префикс `upsert*`:
  - `upsertApartment`, `upsertRoom`, `upsertBlockingContract`.
- Для паттерна «получить или создать» используем `getOrCreate*`:
  - `getOrCreateBuilding`.
- Для переменных с ответами API используем короткий формат:
  - `aptRes`, `contractRes`, `contactRes`.
- Для часто используемых сущностей применяем согласованные сокращения:
  - `apt` (apartment), `map` (field mapping), `typeId` (entity/contract type id).
- Избегаем длинных имен с `ById` в entry-функциях, если контекст уже однозначен:
  - `syncApartment`, `syncTenantContract`, `syncLandlordContract`, `syncContact`, `syncBlocking`, `syncTermination`.

Эти правила применяются к новым изменениям и рефакторингу без изменения бизнес-логики.

### 10.1. Актуальные имена методов (после рефакторинга)

Ниже зафиксированы рабочие имена, которые должны использоваться в коде и документации:

- `UnitApi::upsertRoom` (вместо старого `createOrUpdateRoom`)
- `AppartApi::upsertApartment` (вместо `createOrUpdateApartment`)
- `AppartApi::getOrCreateBuilding` (вместо `createOrGetBuilding`)
- `AppartApi::archiveBuildingIfEmpty` (вместо `tryArchiveBuildingIfAllUnitsArchived`)
- `TenantContractApi::upsertBlockingContract` (вместо `createOrUpdateBlockingContract`)
- `BaseApi::getUnitIdByAptExternalId` (вместо `getUnitIdByApartmentExternalId`)
- entry-функции:
  - `syncApartment`, `syncTenantContract`, `syncLandlordContract`
  - `syncContact`, `syncBlocking`, `syncTermination`

## 11. Точки входа (эндпоинты)

Все эндпоинты отдают JSON через `BaseApi::sendSuccessResponse`/`sendErrorResponse`.

- `POST /index.php`  
  Главный webhook-роутер Bitrix24. Принимает событие в `$_REQUEST`, определяет сущность и проект, дальше вызывает нужный сценарий (`syncApartment`, `syncContact`, `syncTenantContract`, `syncLandlordContract`).

- `GET /Api/AppartApi.php?id=<ID>&project=<Dubai|HongKong>&entity_type_id=<optional>`  
  Синхронизация апартамента в Alma.
  - `id` (обязательно): ID апартамента в Bitrix24
  - `project` (опционально): проект, по умолчанию `Dubai`
  - `entity_type_id` (опционально): переопределение `entityTypeId`

- `GET /Api/RoomApi.php?id=<ID>&project=<Dubai|HongKong>`  
  Синхронизация комнаты/юнита.
  - `id` (обязательно): ID юнита в Bitrix24
  - `project` (опционально): проект, по умолчанию `Dubai`

- `GET /Api/TenantContractApi.php?id=<ID>&project=<Dubai|HongKong>`  
  Синхронизация договора арендатора.
  - `id` (обязательно): ID контракта в Bitrix24
  - `project` (опционально): проект, по умолчанию `Dubai`

- `GET /Api/LandlordContractApi.php?id=<ID>&project=<Dubai|HongKong>`  
  Синхронизация договора собственника.
  - `id` (обязательно): ID контракта в Bitrix24
  - `project` (опционально): проект, по умолчанию `Dubai`

- `GET /Api/ContactSync.php?id=<ID>&project=<Dubai|HongKong>&type=<tenant|landlord>`  
  Синхронизация контакта в Alma.
  - `id` (обязательно): ID контакта в Bitrix24
  - `project` (опционально): проект, по умолчанию `Dubai`
  - `type` (опционально): `tenant` или `landlord`, по умолчанию `tenant`

- `GET /Api/BlockingAppartApi.php?id=<LIST_ELEMENT_ID>&project=<Dubai|HongKong>&debug=1`  
  Синхронизация блокировки из элемента списка Bitrix24.
  - `id` (обязательно): ID элемента списка
  - `project` (опционально): проект, по умолчанию `Dubai`
  - `debug` (опционально): если передан, отдает payload без записи контракта

- `GET /Api/TerminationAppartApi.php?id=<LIST_ELEMENT_ID>&project=<Dubai|HongKong>`  
  Синхронизация расторжения из элемента списка Bitrix24.
  - `id` (обязательно): ID элемента списка
  - `project` (опционально): проект, по умолчанию `Dubai`

## 12. Порядок синхронизации и зависимости

Рекомендуемый порядок для стабильной интеграции:

1. **Апартаменты**: `syncApartment`  
   Создает/обновляет апартамент в Alma и здание (`getOrCreateBuilding`).

2. **Комнаты/юниты**: `syncRooms` или `RoomApi.php`  
   Зависят от уже синхронизированного апартамента в Alma (нужен `parent_unit`).

3. **Контакты**: `syncContact`  
   Желательно синхронизировать до контрактов, чтобы клиент в Alma уже существовал.

4. **Контракты арендаторов**: `syncTenantContract`  
   Зависят от:
   - существующего юнита/апартамента в Alma;
   - существующего клиента в Alma (или возможности создать/обновить его).

5. **Контракты собственников**: `syncLandlordContract`  
   Зависят от апартамента/юнита в Alma и существующего контакта собственника.

6. **Служебные контракты**:
   - `syncBlocking` — блокировки из списка Bitrix24;
   - `syncTermination`/`syncTerminationForApt` — расторжения.
   Оба сценария зависят от корректных маппингов в `ProjectMapping` и от существования объекта в Alma.

## 13. Быстрая диагностика

Минимальный чек-лист при проблемах:

- Проверка синтаксиса измененных файлов:
  ```bash
  php -l Api/AppartApi.php
  php -l Api/TenantContractApi.php
  php -l Api/LandlordContractApi.php
  ```

- Быстрая проверка, что старые имена не остались:
  ```bash
  rg "createOrUpdate|createOrGet|sync[A-Za-z]+ById|getUnitIdByApartmentExternalId" .
  ```

- Просмотр логов:
  - Основной путь: `logs/`
  - Смотри лог за нужный проект и дату, затем фильтруй по ID сущности (apartment/unit/contract/contact).

- Проверка доступности конфигурации:
  - `config.env` содержит валидные `ALMA_API_KEY`, `ALMA_API_URL`, `PROJECT_*_WEBHOOK_URL`
  - Маппинги в `Core/Config/ProjectMapping.php` соответствуют реальным полям Bitrix24.

Частые причины падений:

- Не передан обязательный `id` в endpoint.
- Не найден связанный объект в Alma (например, юнит/апартамент еще не синхронизирован).
- Неверный `project` или устаревшие ID/поля в `ProjectMapping`.
- Конфликт бизнес-правил Alma (пересечение контрактов, дубли email, обязательные поля контакта).
